# Notifications — How to use the platform notification system

This document explains the core concepts and shows examples for registering, defining, and sending notifications in the application.

## Core concepts
- **NotificationRegistry** — register and discover notification definitions (keys, labels, descriptions).
- **NotificationChannelRegistry** — register channel implementations (adapters/factories) such as `database`, `mail`, `sms`, `push`.
- **NotificationDispatcher** — sends an application-level `NotificationMessage` to one or more channels and returns `ChannelResult`s.
- **RegistryBridgeChannel** — Laravel Notification channel bridge. Use this in `via()` to connect a Laravel `Notification` to the registry/dispatcher and user preferences.
- **NotificationMessage** — transport-agnostic DTO representing a notification (type, title, body, recipients, metadata, etc.).
- **ChannelMessage / ChannelResult** — channel-specific payload and delivery result objects.

## Register notification definitions
Each domain exposes notification definitions (key, label, description, supported_channels). Register them from the domain service provider during boot: the pattern is already used by domains such as Projects and Timecards.

Example (domain service provider):

```php
$notificationRegistry->registerDefinitions(ProjectNotificationDefinitions::definitions());
```

A definitions array looks like:

```php
[
  ['key' => 'projects.access-granted', 'label' => 'Project Access Granted', 'description' => 'Sent when a user is granted access', 'supported_channels' => ['mail','database','sms','push']],
]
```

## Implement a domain Notification (Laravel style)
Create a Laravel `Notification` that implements `App\\Core\\Notification\\Contracts\\RegistryNotification`. Return `RegistryBridgeChannel::class` from `via()` so the system consults user preferences and dispatches through the registry.

Example (existing): [app/Domains/Projects/Notifications/ProjectAccessGrantedNotification.php](app/Domains/Projects/Notifications/ProjectAccessGrantedNotification.php)

Key points from the example:
- Implement `notificationKey(): string` returning the definition key.
- Implement `toNotificationMessage(object $notifiable): NotificationMessage` to convert domain data into the `NotificationMessage` DTO (title, body, data, recipients, metadata).
- `via()` should return `[RegistryBridgeChannel::class]` for user-aware delivery.
- Add channel-specific helpers (e.g. `toSms()`), if your channels use them.

Usage (send to a user):

```php
$user->notify(new ProjectAccessGrantedNotification($project));
```

The `RegistryBridgeChannel` will:
- resolve the supported channels
- consult `NotificationPreferenceService` to determine enabled channels for the recipient
- normalize channel names (e.g. webpush → `push`, SmsChannel class → `sms`)
- call `NotificationDispatcher::dispatch()` with a `NotificationMessage` and the final channel list

## Registering and implementing channels
- Built-in adapters are registered in `NotificationServiceProvider` (for example the `database` adapter).
- To add a new channel, register it in the `NotificationChannelRegistry` (usually from a provider):

```php
$registry->register('sms', SmsChannel::class);
```

- Channels implement `App\\Core\\Notification\\Contracts\\NotificationChannel` and must provide `convert(NotificationMessage): ChannelMessage` and `send(ChannelMessage): ChannelResult`.

See the built-in database adapter: [app/Core/Notification/Channels/DatabaseChannelAdapter.php](app/Core/Notification/Channels/DatabaseChannelAdapter.php)

## User preferences and settings
- Preferences UI: `app/Core/Notification/Livewire/Settings/Preferences.php` (route: *Settings → Notifications* in the UI).
- Preferences are stored per-user in `user_notification_preferences` and resolved via `NotificationPreferenceService`.
- Admins can restrict allowed channels per-notification via settings keys generated by `NotificationSettings::allowedChannelsSettingKey($notificationKey)`.
- Master switches and defaults live in settings: `notifications.enabled` and `notifications.default_channels`.

## Direct dispatching (advanced)
If you need to dispatch programmatically without creating a Laravel `Notification`, you can construct a `NotificationMessage` and call the dispatcher directly (container-resolve `NotificationDispatcher`).

Example:

```php
use App\\Core\\Notification\\DTO\\NotificationMessage;
use App\\Core\\Notification\\Services\\NotificationDispatcher;

$message = new NotificationMessage(
    type: 'projects.access-granted',
    title: 'Project Access Granted',
    body: 'You have access',
    data: ['project_id' => (string) $project->id],
    recipients: ['email:'.$user->email, 'phone:'.$user->phone]
);

$dispatcher = app(NotificationDispatcher::class);
$results = $dispatcher->dispatch($message, ['mail','database']);

// $results is an array of ChannelResult keyed by channel name
```

## Testing
- Use `Notification::fake()` in tests when triggering domain notifications through Laravel's `notify()` API.
- Unit-test channels by constructing `NotificationMessage` and asserting `NotificationDispatcher` returns expected `ChannelResult`s (see `app/Core/Notification/Tests`).
